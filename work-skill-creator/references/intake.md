# 1단계 - 업무 파악

목표: 이 업무를 **코드 · 클로드 · 사람** 몫으로 나눈 업무 분해표를 만들고 사용자 확인을 받는다.
분해표가 정확할수록 2 · 3단계가 짧아진다. 모르는 것은 지어내지 말고 분해표의 '확인 필요'에 적는다.

## 1. 묻는 것

한 번에 3개 이내로 나눠 묻는다. 대화에 이미 답이 있으면 묻지 않고 확인만 받는다.

**결과물**
- 무엇을 만드나(파일 · 시트 · 쪽), 누가 받고 누가 검토하나
- 주기(매월 · 매 분기 · 반기 · 매년 · 수시)와 마감, 지금 한 번에 걸리는 시간
- 회계연도가 12월에 끝나는가(3월 · 6월 결산이면 분기 번호 · 연초 처리가 달라진다 - `W.Period(…, fy_end=3)`)
- 받는 사람이 수식이 든 파일을 받는가, 값만 받는가(ERP 업로드 · CSV · 제출 양식이면 작업 파일과 제출 파일을 나눈다)

**자료** - 아래 ①~⑤를 받는다. 받은 자료는 작업 폴더 `01_받은자료` 에 **복사**해 두게 한다(원본 자리는 건드리지 않는다).
| 번호 | 자료 | 쓰임 |
|---|---|---|
| ① | 지난 기간 완성본(사람이 만든 최종본, 제출 · 확정본) | 정답 기준 - 값은 비교에만 |
| ② | ①을 만들 때 쓴 원자료(ERP 내려받기 · 명세서 · 은행 자료 · 계약서 …) | 다시 만들 재료 |
| ③ | 그 전 기간 완성본 | 이어받기 틀 · 기초 이월 |
| ④ | 작업 절차(메모 · 체크리스트 · 말) + 자주 틀리는 곳 · 검토 지적 | 규칙 · 재발 방지 |
| ⑤ | (있으면) 다음 기간 원자료 | 5단계 시험 |

- ①이 여러 판(v1 · v2 · 날짜 · '최종')이면 **실제로 제출 · 확정된 판**이 무엇인지 사용자에게 묻는다. 중간 판을 기준으로 삼으면 맞출수록 틀린다.

**절차** - "처음부터 끝까지 순서대로 말해 주세요"로 묻고, 메모 파일이 있으면 그것을 읽는다.
- 매번 손으로 고치는 곳은? 매번 확인하는 숫자는(대사 · 검산)?
- 가끔 생기는 일은? (새 계약 · 상환 · 만기 · 새 거래처 · 새 계정 · 연초 · 1분기만 하는 일)
- 검토자에게 지적받은 적 있는 곳은? 지난번에 틀렸던 곳은?

**판단** - "기간마다 사람이 정하는 것"을 따로 묻는다(환율 확정 · 명단 · 손실률 · 결론 · 회수 예상 · 할인율).

## 2. 도구로 먼저 보기

질문만으로는 놓치는 것이 많다. 자료를 받으면 바로 돌려 보고, 결과를 질문의 재료로 쓴다.

```
python -X utf8 "<스킬>/scripts/inventory.py" "<작업 폴더>"
python -X utf8 "<스킬>/scripts/compare_xlsx.py" --period "<③ 그 전 완성본>" "<① 지난 완성본>"
python -X utf8 "<스킬>/scripts/xlsx_profile.py" "<① 지난 완성본>" --labels
```

- **inventory** - '기간 묶음'에서 ①②③ 후보를 고른다. 같은 묶음에 판이 여러 개면 사용자에게 확인.
- **기간 비교** - 사람이 기간마다 손댄 곳이 드러난다.
  - '사람이 기간마다 넣은 값' → 원자료 · 이월 · 판단값 · 기간 문구 중 무엇인지 하나씩 분류한다.
  - '늘어난 행' → 명세 · 명단처럼 행 수가 바뀌는 표 → 코드가 행을 늘리고 줄여야 한다.
  - '수식에서 숫자만 바뀐 칸' → 대개 행 수 · 기간 시트 이름을 따라간 것(코드가 다시 쓴다).
  - '수식 구조 바뀜' · '수식이었다가 값이 된 칸' → 계산 방법이 바뀌었거나 손으로 덮어쓴 곳 - **반드시 사용자에게 묻는다**.
- **구조 점검** - 그림 · 메모 · 배열수식 · 외부 연결이 있으면 2단계에서 엑셀(COM)로 고칠지 정한다. 이름표 목록은 코드가 위치를 찾을 때 쓴다.
- PDF · 워드 원자료는 클로드가 직접 읽는다. 숫자를 뽑아 쓸 때는 어느 쪽 · 어느 줄인지 함께 적는다.

## 3. 누가 할지 나누기

질문 하나로 가른다 - **"규칙으로 적을 수 있나?"** 적을 수 있으면 코드, 못 적으면 클로드나 사람.
클로드와 사람은 **"결과에 책임이 따르나?"** 로 가른다. 따르면 사람이 정하고, 클로드는 근거와 후보를 준비한다.

| 일 | 누가 | 이유 |
|---|---|---|
| 원자료를 새 시트로 붙이고 수식 범위를 늘린다 | 코드 | 매 기간 같은 방법이어야 한다 |
| 구간별로 계산하고 대사한다 | 코드 | 계산 규칙이 정해져 있다 |
| 외부 조회(국세청 휴폐업 · 환율 고시 · 공시)를 하고 정해 둔 규칙대로 반영한다 | 코드 | 사람이 정해 둔 정책을 적용할 뿐이다 |
| 비고 칸의 "어음 부도"를 읽고 위험 거래처를 표시한다 | 클로드 | 글을 읽고 해석해야 한다 |
| 새 계약이 리스인지 기준서 문단을 찾아 판단 초안을 쓴다 | 클로드 | 근거를 찾아 설명해야 한다 |
| 새 ERP 계정을 기존 계정표에 짝짓는 안을 낸다 | 클로드 | 이름 · 성격을 보고 골라야 한다 |
| 명단에 넣을지 · 손실률 · 결론 · 정책을 정한다 | 사람 | 결과에 책임이 따른다 |

**경계 사례**
- 정책 적용 vs 정책 결정: "폐업이면 100%"를 **적용**하는 것은 코드, 그 정책을 **정하거나 바꾸는** 것은 사람.
- 후보 vs 확정: 기말 환율 후보를 자료에서 찾아 근거와 함께 보여 주는 것은 코드 · 클로드, 확정은 사람(한 번 확정하면 모든 업무가 같은 값을 쓴다 - build-rules.md '공유 확정값').
- 짝짓기 표: 이미 정해진 짝(매핑 표)을 적용하는 것은 코드, 새 항목 짝짓기 제안은 클로드, 확정은 사람 → 확정한 짝은 매핑 표 파일에 추가해 다음부터 코드가 적용한다.
- 문장: 숫자를 채우는 문구 틀은 코드, 문장 초안은 클로드, 제목 · 핵심 메시지 승인은 사람.
- 판단이 하나도 없으면 클로드도 뺀다 - 스크립트만으로 돌고, 예약 작업으로 자동 실행할 수 있다.

## 4. 기간마다 바뀌는 값 분류

| 종류 | 예 | 처리 |
|---|---|---|
| 자동 | 기준일 · 기간 문구 · 기초(지난 기간 결과) · 행 수 | 코드 - 기준일 칸 하나만 바꾸고 나머지는 수식 |
| 원자료 | 명세서 · 시산표 · 은행 평가표 | 코드 - `Data_` 시트에 그대로 |
| 판단값 | 환율 · 할인율 · 회수 예상 · 명단 · 손실률 | 사람 - 판단 입력 파일, 클로드는 후보와 근거 |
| 고정 | 양식 · 계정코드 · 설정률표 · 회사 정책 | 이어받기 - 바뀌면 사람이 고치고 스킬도 고친다 |
| 연간 | 연초 갱신(회수 실적 · 사업계획 · 요율) | 첫 기간에만 - 해당 기간이면 멈추고 묻는다 |

## 5. 멈춤 조건 찾기

다음을 하나씩 물어 멈춤 · 경고 목록을 만든다.
- 원자료가 없거나 기준일이 다르면? 지난 완성본이 없으면?
- 지난 기간에 없던 항목(새 계약 · 새 계정 · 새 거래처 유형 · 새 법인)이 생기면?
- 상환 · 만기 · 해지 · 1년 이내 만기(유동성 대체)처럼 구조가 바뀌는 일은?
- 대사(장부 · 명세 · 원자료 합계)가 안 맞으면? - 맞춰서 넘기지 않고 '확인 필요'로 표시한다.

## 6. 업무 분해표 쓰기 → 확인 ✋

`assets/plan-template.md` 를 `02_작업/분해표_<업무>.md` 로 복사해 채운다. 사용자에게 들은 작업 절차는 `02_작업/절차_<업무>.md` 에 그대로 옮겨 두고, 2단계에서 업무 스킬의 `references/procedure.md` 로 옮긴다.
사용자에게 보여 주고 확인받을 것:
- 단계 표(누가 · 이유)와 사람이 정할 것 목록
- 정답 기준(①) · 틀(③) · 원자료(②) 파일 이름
- 스킬 이름(영문 소문자 · 하이픈, 예: `allowance-quarter`) · 위치(프로젝트 / 전역) - **여기서 확정한다**
- '확인 필요'로 남긴 것

비슷한 업무를 `references/examples.md` 에서 찾아 나누기의 출발점으로 쓴다. 예시에 있는 단계(예: 외부 조회)라도 이 업무의 작업 절차에 없으면 넣지 않고, 넣을지 사용자에게 묻는다.

## 7. 특별한 출발점

**방금 대화로 업무를 끝낸 경우("방금 한 거 스킬로")**
대화 기록에서 다음을 뽑아 분해표 초안을 쓰고 확인받는다: 쓴 자료 · 순서 · 쓴 코드 · **사용자가 고쳐 준 것**(= 판단이거나 빠진 규칙) · 결과 파일.
대화 중 만든 코드가 있으면 2단계에서 업무 스킬 `scripts/` 로 옮겨 정리하고, 맞출 기준이 있으면 3단계부터 한다.
기준 완성본이 없다면 대화로 만든 결과를 사용자가 확인해 기준으로 삼는다(아래).

**①은 있는데 ③(그 전 기간 완성본)이 없는 경우** - 한 번만 해 본 업무
①의 사본에서 입력 칸(원자료 · 판단값 · 기간 문구 · 기초 이월)을 모두 비워 틀로 쓴다. 비운 칸 목록을 사용자에게 확인받는다.
이 재현은 '비운 입력 칸을 코드가 다시 채울 수 있는지'만 확인한 것이므로, 다음 기간에 사람이 결과를 검토할 때까지는 검증이 약하다고 업무 스킬 6절에 적는다.

**지난 완성본이 없는 새 업무**
처음 한 번은 대화로 같이 만든다 → 사용자가 검토하고 고친다 → **사용자가 확정한 파일을 기준(①)으로 삼는다.**
사용자가 고친 칸은 규칙(코드에 넣음)인지 판단(판단 입력 파일)인지 하나씩 가른다(excel-sync 스킬이 있으면 고친 칸 찾기에 쓴다).
다음 기간부터는 정상 흐름(재현 → 맞추기)으로 간다. 그때까지 '검증 = 내부 검산 + 사람 검토'임을 SKILL.md 6절에 적는다.

**절차가 사람마다 다르거나 정해져 있지 않은 업무**
먼저 사용자와 절차를 한 가지로 정한다(`02_작업/절차_<업무>.md` 에 적고, 2단계에서 업무 스킬 `references/procedure.md` 로 옮긴다). 절차가 정해지지 않은 업무는 자동화할 수 없다.
